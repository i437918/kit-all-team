# Дизайн hotfix v0.1.1 для установки Hermes

## Цель и границы

`v0.1.1` исправляет только совместимость профилей Hermes, обнаруженную после
выпуска `v0.1.0`. Hotfix не меняет защищённый тег, существующий GitLab Release,
job artifacts и подтверждения `v0.1.0`: идентичность выпуска связывают
защищённый тег, записанный exact SHA и хеши, а не операционно изменяемые metadata
GitLab Release/job. Исправление выпускается новым финальным релизом `v0.1.1`.

Hotfix не меняет каталог проектов, выбор ролей и toolchain, Git-сценарии,
секреты, реестр окружений или поддержку платформ. Никакой связанный рефакторинг
и новое пользовательское поведение вне описанного ниже в выпуск не входят.

## Создание профиля и сосуществование skills

Новый профиль создаётся штатной командой Hermes:

```text
hermes profile create <id> --no-alias
```

Флаг `--no-skills` запрещён в обоих местах, где его передаёт `v0.1.0`: из
`ProfileCLI` и из вызова POSIX `install.sh`. После managed-установки в корне
Hermes нет `.no-bundled-skills`, штатные bundled skills посеяны. Bundled skills
Hermes остаются в профиле, а Team Kit добавляет ровно один выбранный внешний toolchain. Lock и readiness внешнего
toolchain связывают только имена каталогов и файлы, перечисленные в
TeamKit-lock. Не относящиеся к lock bundled-каталоги разрешены, не обходятся для
хеширования и никогда не удаляются или перезаписываются Team Kit.

Если bundled или пользовательский каталог имеет имя, которое должен установить
выбранный внешний toolchain, Team Kit останавливается с
`HERMES_TOOLCHAIN_NAME_COLLISION`. Он не пытается объединить содержимое,
переименовать каталог или определить владельца по содержимому. Второй
TeamKit-lock другого toolchain также остаётся fail-closed ошибкой.

Для нового профиля collision проверяется по уже созданным bundled-каталогам до
записи внешних skills. Перед миграцией read-only inventory строится только из
`<verified-install-root>/skills`: это bundled source того же Install directory,
который сообщил exact проверенный executable. Адаптер не принимает переменные
окружения и не следует symlink/reparse point, ограничивает число каталогов,
глубину, число файлов и общий объём прочитанных `SKILL.md`; имя берётся из
ограниченного frontmatter и пути ровно по правилам установленного
`tools/skills_sync.py`. Если поставка содержит bundled manifest, он также
читается только из этого install root с теми же пределами и обязан точно
совпасть с inventory. Team Kit связывает inventory с identity executable и
file identity install root, затем сравнивает имена с `InstalledSkills` своего
lock до `opt-in`. Missing/foreign/reparse/oversize/duplicate inventory даёт
`HERMES_BUNDLED_SKILLS_CATALOG_UNVERIFIED` без запуска миграции.

Установка внешнего toolchain — возобновляемое слияние, а не замена `skills/`.
Сначала полный preflight имён, затем до первого переноса создаётся атомарный
owner-only `.teamkit/toolchain.pending.json` с pin, полным manifest, именами,
хешами и nonce операции. Для каждого имени уже существующий каталог принимается
только если он принадлежит этому pending/final lock и точно совпадает с manifest;
любое другое совпадение имени — collision. Отсутствующий каталог атомарно
переименовывается из path-safe staging. После каждого каталога атомарно
обновляется progress внутри owner-only `toolchain.pending.json`;
action/effect checkpoint не продвигается. Прерывание после pending lock или любого rename
безопасно продолжается через `retry`. Final lock публикуется атомарно и pending
удаляется только после полного совпадения всех owned-каталогов; лишь после этого
продвигается action/effect checkpoint. Readiness требует полный final lock;
bundled/foreign каталоги и их хеши до и после операции неизменны.

## Миграция профилей v0.1.0

Миграция разрешена только для профиля с точным TeamKit ownership proof:
совпадают identity, опубликованный owner record либо актуальный nonce-bound
claim, выбранный проект, роль, toolchain и ожидаемые неперенаправленные пути.
Наличие `.no-bundled-skills` само по себе недостаточно. Team Kit открывает marker
no-follow как обычный не-reparse файл, ограниченный 256 байтами, и принимает
только точные UTF-8 байты, которые Hermes создаёт командой
`profile create --no-skills`:

```text
This profile opted out of bundled-skill seeding (`hermes profile create --no-skills`).
Delete this file to re-enable sync on the next `hermes update`.
```

Допустимы только точные окончания LF или их Windows-вариант CRLF. Другие байты,
даже при том же имени marker, считаются пользовательским opt-out и никогда не
переопределяются автоматически: возвращается `HERMES_BUNDLED_SKILLS_USER_OPT_OUT`.
Точный marker в доказанном owned-профиле запускает единственный разрешённый API:

```text
hermes -p <identity> skills opt-in --sync
```

Это документированный Hermes 0.20.1 способ удалить marker и немедленно штатно
восстановить bundled skills. Общий `hermes update`, ручное копирование bundled
или Learned skills, пересоздание профиля и очистка каталогов запрещены. Sessions,
пользовательские данные и не принадлежащие Team Kit файлы не изменяются.

После успешной команды Team Kit проверяет, что marker отсутствует, ownership
profile root не изменился, а выбранный внешний toolchain по-прежнему совпадает
с lock. Ошибка, таймаут или повторное появление marker дают
`HERMES_BUNDLED_SKILLS_MIGRATION_FAILED`; same-name collision возвращает
`HERMES_TOOLCHAIN_NAME_COLLISION`. Текущий effect не получает успешный
checkpoint. Для foreign profile или недоказанного ownership возвращается
`FOREIGN_HERMES_PROFILE` без запуска Hermes и без записи файлов.

Миграция является идемпотентным compatibility-precondition действий
`50-configure-application` и `90-verify-state`, а не новым номером action. Поэтому
`retry` продолжает как операции, остановленные на Action 50, так и старую
операцию, в которой незавершён только Action 90. При обычном `update` точный
owned marker делает application state неготовым и планирует Action 50. После
первого успешного opt-in marker отсутствует, и повторный `retry`/`update` не
запускает миграцию снова.

## Безопасная публикация staging-профиля

Hermes может создать `.env` внутри staging-профиля с наследуемой DACL. До
adoption Team Kit нормализует этот файл в owner-only состояние. Операция
разрешена только пока строгий nonce-bound ownership claim доказывает, что именно
этот staging identity и каталог созданы текущей операцией.

На Windows файл открывается без следования reparse point, DACL и owner меняются
на том же handle без чтения или перезаписи содержимого, затем на том же handle
повторно подтверждается единственная FullControl ACE текущего пользователя,
выключенное наследование и неизменные размер/хеш `.env`. На POSIX тот же контракт
обеспечивается открытым file descriptor, режимом `0600` и неизменными байтами. Подмена
пути, symlink/junction, несовпадение file identity или ACL после записи дают
существующий `SECRET_FILE_PERMISSIONS_UNSAFE`; adoption не выполняется. Уже
существующий foreign profile и его `.env` никогда не нормализуются автоматически.

## Конфигурация и Doctor

Поддерживаемый runtime остаётся `>= 0.20.1` и `< 0.21.0`, но semver не определяет
schema. `ConfigSchemaProbe` от verified executable получает тот же exact Install
directory и no-follow открывает только
`<verified-install-root>/hermes_cli/config_defaults.py`: обычный не-reparse файл
не более 512 KiB с неизменной file identity. Ограниченный parser не исполняет
Python и принимает ровно одно целочисленное значение `_config_version`; разрешены
только прошедшие аудит schema 34 и 37. Missing, duplicate, malformed, иное число,
подмена пути или выход за пределы дают `HERMES_CONFIG_SCHEMA_UNSUPPORTED` до
записи config. Renderer использует доказанное значение: managed runtime из
закреплённого commit `f80f453ae0679347e38abc917c7f94f717bf96c5` остаётся
schema 34, а наблюдаемый Windows Hermes
0.20.1 — schema 37; repin Hermes в hotfix не выполняется. Перед записью Team Kit
проверяет поля CustomLLM, модель `generic-development`, MCP `v8std`, рабочий
каталог и отсутствие секретного значения в `config.yaml`.

Read-only capability contract также сужается: `profile create --help` обязан
подтверждать `--no-alias`, а `skills opt-in --help` — `--sync`. Наличие
`--no-skills` больше не является требованием совместимости и этот флаг никогда
не передаётся при создании профиля.

Doctor не классифицирует предупреждения по смыслу. Его subprocess ограничен по
времени и объёму; start failure, timeout и ненулевой exit code дают
`HERMES_PROFILE_DOCTOR_FAILED`. После удаления только ANSI-кодов parser exit 0
принимает точный terminal footer `All checks passed! 🎉` либо terminal block
`Found N issue(s) to address:` и ровно N непустых нумерованных строк `1.`…`N.`
как ограниченную диагностику; после списка допускается только точная штатная
строка `Tip: run 'hermes doctor --fix' to auto-fix what's possible.`. Несовпавшие
количество/нумерация, неизвестная строка внутри terminal block,
повреждённый/усечённый block или иные данные после него остаются fail closed с
тем же кодом. Содержимое records не классифицируется и не ослабляет или усиливает
решение.

Независимо от текста Doctor Action 90 fail-closed проверяет до и после subprocess
принадлежащие Team Kit инварианты: подтверждённый runtime, owner-only secrets,
config с доказанной schema 34/37,
provider/model/v8std, ownership profile и lock с файлами выбранного внешнего
toolchain. Их нарушение даёт `HERMES_MANAGED_INVARIANT_FAILED`. Unrelated Doctor
warnings записываются только как ограниченная несекретная диагностика и не
блокируют готовность.

## Коды ошибок

- `HERMES_TOOLCHAIN_NAME_COLLISION` — имя внешнего skill или lock уже занято.
- `HERMES_BUNDLED_SKILLS_CATALOG_UNVERIFIED` — read-only inventory bundled
  skills не удалось связать с проверенным runtime; запись не начинается.
- `HERMES_BUNDLED_SKILLS_MIGRATION_FAILED` — штатный opt-in не завершён или не
  дал проверяемого результата.
- `HERMES_BUNDLED_SKILLS_USER_OPT_OUT` — marker не совпадает с точным marker
  Hermes, поэтому пользовательский opt-out сохранён без мутаций.
- `FOREIGN_HERMES_PROFILE` — ownership профиля или staging не доказан; мутаций нет.
- `SECRET_FILE_PERMISSIONS_UNSAFE` — owner-only нормализация staging
  `.env` не подтверждена.
- `HERMES_CONFIG_SCHEMA_UNSUPPORTED` — runtime и schema конфигурации несовместимы.
- `HERMES_PROFILE_DOCTOR_FAILED` — Doctor не запустился, завершился ошибкой или
  превысил пределы.
- `HERMES_MANAGED_INVARIANT_FAILED` — нарушен управляемый Team Kit контракт
  профиля при Action 90.

Ошибки не содержат токены, содержимое `.env`, сессии или произвольный вывод
Hermes. Failed effect сохраняет красную квитанцию и возобновляется через
`retry`, без удаления профиля.

## Тестовая матрица

1. ProfileCLI создаёт новый профиль с `--no-alias` и без `--no-skills`; POSIX
   installer также вызывается без `--no-skills`. Capability probe требует
   `--no-alias` и `skills opt-in --sync`, но не `--no-skills`; managed home не
   содержит marker и получает bundled skills.
2. Bundled skills и каждый из двух внешних toolchain сосуществуют; readiness
   игнорирует unrelated bundled dirs, но выявляет изменение каждого owned файла.
3. Same-name skill, второй lock, symlink/junction и подмена файла fail closed;
   снимок чужих каталогов до/после идентичен.
4. Exact regular owned marker с LF и CRLF вызывает ровно `skills opt-in --sync`;
   повторный запуск является no-op. Отличающийся одним байтом, oversized,
   reparse и foreign marker не запускают процесс. Learned skills, sessions и
   user data сохраняют хеши.
5. Legacy receipts с незавершёнными Action 50 и только Action 90 мигрируются
   через `retry`; `update` планирует миграцию, а сбой не продвигает checkpoint.
6. Windows same-handle тесты покрывают наследуемую DACL, path replacement,
   junction и foreign staging; POSIX — `0600`, symlink и inode replacement.
7. Одинаковая версия Hermes с fixtures schema 34 и 37 получает разные корректные
   config; Windows 0.20.x schema 37 и managed
   `f80f453ae0679347e38abc917c7f94f717bf96c5` schema 34 проходят.
   Unknown/missing/multiple schema fail до записи и не меняют профиль.
8. Exit-zero Doctor принимает exact success либо complete N/N diagnostics;
   неверный count, unknown/truncated output, subprocess, runtime,
   provider/model/v8std, secret ACL и toolchain failures блокируют.
9. Fault-injection после pending lock и каждого atomic directory rename
   подтверждает идемпотентный `retry`, полный final lock и неизменные хеши
   bundled/foreign каталогов.
10. README и `docs/INSTALL.md` описывают текущий `v0.1.1` до неизменённого
   исторического архива RC2 и направляют владельцев `v0.1.0` на `retry`/`update`.

## Приёмка релиза

- Полные `go test -mod=vendor -count=1 ./...`, `go vet -mod=vendor ./...`,
  security audit и кросс-платформенная сборка проходят для одного exact SHA.
- Нативные Windows/Linux/macOS проверки и существующая ALT userspace-проверка
  проходят с прежними явно указанными ограничениями платформ.
- Чистая установка сохраняет bundled skills и добавляет один внешний toolchain.
- `retry` и `update` безопасно восстанавливают exact TeamKit-owned профили
  `v0.1.0` без потери sessions, Learned skills или пользовательских данных.
- Hotfix не меняет `docs/releases/v0.1.0.md`, защищённый тег, существующие
  Release/job artifacts `v0.1.0`, исторические RC2-разделы, ссылки, байты и
  contracts. Идентичность `v0.1.0` задают защищённый тег и записанные SHA/хеши;
  metadata GitLab Release и job остаются операционно изменяемыми.
- `v0.1.1` проходит exact-SHA GitLab CI и полный GitHub CI; все шесть файлов
  публикации из обоих контуров — четыре бинарника, `SHA256SUMS` и
  `SECURITY-AUDIT.json` — сравниваются byte-for-byte, а публикуются байты сохранённого
  (`kept`) GitLab job. После успеха создаются новый защищённый tag `v0.1.1` и
  новый GitLab Release, не перемещается ни один прежний tag.
- В `Assets -> Other` нового Release остаются ровно две существующие
  вспомогательные ссылки: `Hermes-Setup.exe` и `certs.zip`; бинарники,
  `SHA256SUMS` и `SECURITY-AUDIT.json` даются колонкой прямых kept-job links в
  release notes. После публикации отдельным docs-коммитом записывается
  `docs/releases/v0.1.1.md` с exact SHA, pipeline/job, ссылками, размерами,
  SHA-256, dual-CI/byte-compare и явно сохранёнными ограничениями платформ.
