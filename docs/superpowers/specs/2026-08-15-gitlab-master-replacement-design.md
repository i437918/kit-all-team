# Дизайн быстрой замены GitLab master

## Цель

Опубликовать текущий Go-проект в защищённой ветке `master` репозитория `https://gitlab.example.invalid/1c/aisuz/ai`, полностью исключив историю прежнего проекта из доступной истории `master`.

## Границы операции

- Удалённая `master` заменяется текущим проверенным `HEAD` локального проекта через `force-with-lease` с ожидаемым старым SHA `a9ccc8bebc87df4fc415934173ed46cd82895ed7`.
- Истории старого и нового проектов не объединяются.
- Все 11 веток `content-*` сохраняются с точными исходными SHA.
- Удаляются старые теги `team-kit-control-plane-windows-20260730`, `v1.0.0`, `v1.0.1`, `v1.1.0`, связанные старые GitLab Releases и пакеты прежнего проекта.
- Устаревший MR `!5` закрывается.
- Другие ветки, настройки доступа, CI variables и проекты не изменяются.

## Порядок

1. Проверить чистоту локального дерева, полные тесты, security audit и отсутствие запрещённых файлов в истории текущего `HEAD`.
2. Сохранить точные SHA `master` и всех `content-*`; остановиться при любом расхождении с зафиксированным состоянием.
3. Временно разрешить force push в защищённую `master` только владельцу.
4. Выполнить один `force-with-lease`, проверить новый SHA и сразу восстановить запрет force push.
5. Сравнить все `content-*` с исходным снимком.
6. После отдельного подтверждения непосредственно перед удалением удалить старые теги, Releases и пакеты, затем закрыть MR `!5`.
7. Проверить pipeline новой `master`. Существующий `.gitlab-ci.yml` выполняет `go vet`, тесты, четыре cross-build и security audit; автоматическая публикация нового GitLab Release остаётся отдельной задачей.

## Результат и отклонения

Доступная история `master` содержит только текущий проект. Старые объекты могут физически оставаться во внутреннем хранилище GitLab до housekeeping, но не доступны через `master`, теги или Releases. При ошибке до force push удалённое состояние не меняется; при ошибке после push защита `master` восстанавливается раньше любых операций очистки.
