# Руководство по репозиторию

## Структура проекта

Точка входа исполняемого файла находится в `cmd/teamkit`; отдельный аудитор безопасности — в `cmd/teamkit-security-audit`. Повторно используемый код размещайте в узких пакетах `internal/`: `catalog` и `domain` задают допустимые конфигурации, `reconcile` вычисляет действия, `service` связывает сценарий, `workspace` и `gitx` управляют рабочим деревом, а `hermes` и `apps` интегрируют AI-клиенты. За безопасность путей, приватных файлов и операций отвечают `pathsafe`, `privatefile`, `secrets` и `operationlock`. Тесты пакета храните рядом с кодом; сквозные сценарии — в `test/`. Скрипты сборки находятся в `scripts/`, документация и подтверждения релиза — в `docs/`.

## Сборка, тестирование и разработка

- `go test ./...` запускает детерминированные модульные и интеграционные тесты.
- `go test -race ./...` проверяет конкурентный доступ на поддерживаемых нативных исполнителях.
- `go vet ./...` выявляет подозрительные конструкции Go.
- `go fmt ./...` применяет стандартное форматирование.
- `go build ./cmd/teamkit` собирает бинарник текущей платформы.
- `make verify` последовательно проверяет форматирование, `vet` и тесты.

Используйте Go 1.26.6. Скрипты релиза задают `CGO_ENABLED=0` и встраивают версию, хеш коммита и дату сборки.

## Стиль и именование

Следуйте `gofmt`, не выравнивайте Go-код вручную. Имена пакетов — короткие существительные в нижнем регистре. Экспортируемые идентификаторы снабжайте комментариями документации. Используйте `PascalCase` для экспортируемых типов, `camelCase` внутри пакета и стабильные коды ошибок в верхнем регистре, например `AI_APP_REQUIRED`. Платформенные различия изолируйте узкими интерфейсами или файлами `_windows.go` и `_unix.go`.

## Требования к тестам

Сначала добавьте падающий тест, затем минимальную реализацию. Именуйте тесты по схеме `TestBehavior_Context`; для матриц каталога используйте табличные тесты, для отказов процессов и файловой системы — подменные адаптеры. Любое изменение, связанное с секретами, должно включать проверку контрольной строки секрета. Проверки реальных GitLab, провайдера или установщика дополняют, но не заменяют автономный набор тестов.

## Коммиты и запросы на слияние

Пишите заголовки Conventional Commits в повелительном наклонении, например `feat(cli): add deterministic plan output`. Каждый коммит должен быть небольшим и проходить проверки. В запросе на слияние укажите изменение поведения, риски, выполненные команды проверки, связанные задачи и подтверждения по платформам; снимки экрана нужны только для видимых изменений интерфейса.

## Безопасность и конфигурация

Не добавляйте в Git `.env`, `db/`, `.teamkit/`, токены, сертификаты или созданные квитанции операций. Team Kit не должен выводить секреты, изменять системные хранилища доверия или записывать изменения напрямую в ветку проекта `develop`.

## Release artifact handoff

Для каждого релиза после первого успешного exact-SHA GitHub CI необходимо ровно
один раз перенести immutable набор `candidate-binaries` и весь required evidence
в GitLab.

- GitLab является единственным источником release-artifacts для publisher и final
  validation: используйте только GitLab pipeline/job/artifact IDs, filenames,
  SHA256 и embedded commit/version.
- Publisher и final validation не должны скачивать bytes GitHub Actions artifact,
  обращаться к `archive_download_url`, ожидать новый GitHub CI или запускать
  `workflow_dispatch` после успешного исходного exact-SHA CI.
- Из GitHub разрешено получать только immutable metadata исходного CI (`run_id`,
  `artifact_id`, `digest`, `head_sha`) для provenance. Отсутствие или
  неоднозначность metadata является fail-closed ошибкой.
- Handoff выполняется ровно один раз для exact SHA и сохраняется через GitLab
  artifact/package с retention/keep. Повторный handoff, повторный publisher и
  перезапись существующих release-объектов запрещены.
- До первой release-мутации проверьте через GitLab API единственный exact artifact
  set, шесть ожидаемых файлов, совпадение SHA256 и embedded version/commit.
- Если реализация отклоняется от этой схемы, остановите работу до изменения
  архитектуры; не компенсируйте отклонение retry, sleep, повторным GitHub CI или
  временными URL.
